# Executive Summary

**Research date:** 2026-07-16  
**Verdict:** **Pursue only through a narrow pilot.**

The investigated thesis is an on-demand proprietary-data resolution layer for AI coding and automation agents: a system that detects when an agent has reached a data-related failure node, identifies the missing proprietary data, brokers licensed minimal access, prevents extraction, meters use, and settles payments. The attractive version is horizontal: every coding agent fails on missing knowledge; many data owners have locked-up content; a neutral broker can sit between agents and rights holders and monetize resolution events. The skeptical conclusion is that this is not a strong horizontal company thesis for coding agents specifically. It may be a useful product shape inside a few regulated or rules-heavy vertical workflows, but the general "agent data marketplace" framing collapses under failure-mode mix, platform control, and incumbent substitutes.

The horizontal thesis fails first because most serious coding-agent failures are not external-data failures. They are prompt/spec failures, architectural mistakes, missing permissions, weak reasoning, insufficient tests, context-window problems, tool-call failures, and non-functional omissions. The Augment/Osmani "80% problem" is a useful framing here: agents often produce the visible functional 80% while skipping production-grade requirements such as security, observability, retries, rate limits, audit logging, PII handling, and architectural consistency. That remaining 20% is usually not buyable data. It is engineering discipline, project context, verification, and human judgment. [Secondary / company-claimed for the published framing; inference for applicability.]

Second, the part of the problem that is public documentation is already being attacked directly inside coding workflows. Context7 by Upstash provides up-to-date, version-specific library documentation and code examples for LLMs and AI code editors through MCP and CLI workflows. It resolves library IDs and retrieves docs into the agent context, addressing stale APIs, hallucinated methods, and outdated examples. That does not solve every doc gap, but it narrows the most obvious generic wedge: public library docs. A new proprietary-data broker should not expect to win by selling "better docs for frameworks" unless those docs are licensed, private, and operationally critical. [Verified for Context7 product claims from Upstash/Context7 docs; inference for wedge impact.]

Third, observability incumbents see failures but do not need to become data brokers to keep their core value. LangSmith and Langfuse already instrument traces, tool calls, prompts, retrieved documents, costs, feedback, and evals for LLM applications. They are well positioned to classify runs, cluster bad traces, and surface root causes. Their product center is monitoring, debugging, evaluation, and dataset creation, not licensing missing external content at run time. A broker can integrate with them, but it is unlikely to out-observe them. If failure detection is the control point, observability vendors can add classification. If data brokerage is the control point, the broker still needs enough observability integration to detect failures accurately. The proposed product is therefore squeezed between observability on one side and data distribution on the other. [Verified for observability capabilities; inference for strategic squeeze.]

Fourth, data distribution and licensing infrastructure is already moving closer to large platforms. Cloudflare acquired Human Native in January 2026 to help AI developers discover, access, and purchase licensed high-quality data from creators and publishers. The strategic implication is not that this startup idea is invalid; it is that broad AI data licensing is attractive enough for infrastructure incumbents to internalize. A standalone horizontal broker would need a narrower workflow-specific wedge where Cloudflare-style crawling, publisher monetization, and training/inference data markets do not satisfy the buyer. [Verified for acquisition; inference for competitive implication.]

Fifth, Snowflake Cortex Knowledge Extensions demonstrate that licensed proprietary content for RAG and agentic systems already has an enterprise distribution pattern. Snowflake describes CKEs as Cortex Search Services shareable on Snowflake Marketplace, private listings, or organization listings, allowing licensed and proprietary content such as articles, market research, books, forum posts, and other unstructured sources to be integrated into Cortex AI applications. Snowflake also supports content-protection thresholds: providers can cap the percentage of indexed corpus a consumer can retrieve within a rolling 24-hour period, blocking queries after the threshold is hit. This is close to one of the proposed platform's most important primitives: minimal access plus anti-extraction limits. It does not handle coding-agent failure detection, but it shows that distribution, entitlements, and content protection are not greenfield. [Verified.]

Sixth, coding platforms already own the workflow surface. Cursor, Claude Code, and GitHub Copilot/VS Code support MCP or comparable tool-connection patterns that let agents call documentation services, databases, internal APIs, browsers, GitHub, issue trackers, and hosted tools in the coding loop. This matters because the proposed broker's best trigger point is inside the agent: when the run fails, the agent asks for missing data. The platforms can expose MCP marketplaces, suggested tools, first-party documentation retrieval, enterprise connectors, and policy controls. They have the run context, user identity, repo context, and approval UX. A third party can still supply a specialized MCP server or vertical connector, but "all agents route failures through us" is structurally weak. [Verified for MCP support in leading platforms from product/docs ecosystem; inference for internalization risk.]

Seventh, many of the strongest vertical data examples are already sold as APIs. Optum's Real Claim Pre-Check API validates X12 837 claims, membership and eligibility, coordination of benefits, prior authorization requirements, claim edits, and medical/payment policies before submission. That is exactly the kind of rules-heavy proprietary or semi-proprietary knowledge that an automation agent may need when building revenue-cycle workflows. But the data owner or domain incumbent can already sell the resolution endpoint. The broker's role is not to invent the data market; it is to route an agent to the right entitlement-gated endpoint, normalize integration, enforce least-privilege use, and prove demand. [Verified for Optum API capabilities; inference for broker role.]

Eighth, pay-per-query pricing already exists in some data verticals. OpenSanctions lists hosted screening API pricing at **€0.10/query** for match/reconcile/search patterns, with free endpoints for entity retrieval and statements and bulk/on-premise options. This is relevant because it proves that small paid data calls can be commercially legible in compliance workflows. It also warns that margins may be thin and buyer willingness to pay depends on risk reduction, not on generic agent convenience. [Verified.]

The resulting market estimate is modest. **Inference:** only about **10-20% of serious coding-agent failures** are plausibly resolved by purchasing external proprietary data. This range is intentionally about serious failures, not all failed completions. The lower bound reflects that many serious failures are engineering-process or project-context failures. The upper bound reflects that in specialized automation domains, missing proprietary rules, private schemas, payer edits, product compatibility matrices, compliance watchlists, or market/pricing feeds can block completion. The percentage would be much lower for general web/backend/frontend coding and much higher inside selected vertical automation workloads.

The strongest wedge, if any, is **vertical domain-rule data inside coding and automation workflows**, not public library docs. Candidate wedges include healthcare revenue-cycle management claim edits and payer policy checks; construction codes, product approvals, and local code interpretations; compliance screening integrations such as sanctions, PEP, adverse media, and beneficial ownership; insurance underwriting and claims rules; tax/payroll/local filing logic; and industry-specific product compatibility or certification datasets. In these settings, the agent is not merely looking up how to call a library. It is trying to implement or automate a process where correctness depends on rules, coverage, entitlement, and provenance. The buyer may pay because wrong output creates claim denials, compliance exposure, failed permits, underpayment, fines, or operational rework. [Inference.]

The weakest assumption is **reliable automated classification of "data-caused" versus other failures**. The proposed loop depends on detecting that a failure node is caused by missing or stale proprietary data rather than bad requirements, low-quality code, missing credentials, an unhelpful prompt, inadequate tests, a hallucinated plan, or a tool error. False positives waste money and annoy users. False negatives make the broker irrelevant. Ambiguous cases are common: an agent may fail to implement payer eligibility logic because it lacks payer policy data, because the user did not specify the payer, because the data is in an internal contract, because the codebase lacks a model for eligibility, or because the agent simply reasoned poorly. This classification problem should be treated as the key pilot risk, not an implementation detail. [Inference.]

Therefore, the recommended path is not to build a generic marketplace, training-data exchange, MCP registry, or observability platform. The recommended path is a **narrow pilot** with one vertical, one or two data owners, one or two coding/automation hosts, and a tightly defined failure class. The pilot should prove that: (1) failure traces can be classified as data-caused with acceptable precision; (2) a licensed minimal-access call resolves the task more often than free search, Context7-style public docs, or human clarification; (3) content can be protected against extraction; (4) buyers will pay per resolved workflow or per query at a rate exceeding data-owner costs and integration support; and (5) the host platform does not immediately internalize the flow.

- **Verified:** Context7/Upstash public-doc retrieval; Snowflake Cortex Knowledge Extensions and content-protection thresholds; Cloudflare acquisition of Human Native in January 2026; Optum Real Claim Pre-Check/claim validation APIs; OpenSanctions €0.10/query pricing; MCP support patterns across major coding-agent hosts.

- **Secondary:** Journalism/analyst summaries and the Augment/Osmani 80% problem writeups.
- **Inference:** 10-20% resolvability estimate; horizontal-thesis weakness; internalization risk; strongest vertical wedge; weakest assumption around automated data-causality classification.
